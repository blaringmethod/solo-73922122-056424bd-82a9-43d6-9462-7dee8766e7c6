# 疾控汇总发布安全审查台

疾控数据员在公开「分区 × 年龄组」汇总检出数前，用本工具审查：**多份已公开汇总叠加后，是否会暴露小样本格（原检出数 1~4）的取值**。技术栈：FastAPI + SQLite + z3-solver。

两台服务实例可共用同一份 SQLite 调查库；确认发布在数据库级写事务内完成
「重读最新公开记录 → 重核 → 原子写入」，因此跨进程也成立。

## 快速开始

### Docker Compose（推荐：两台共享库的实例）

```bash
docker compose up --build
```

| 实例 | 内部审查台 | 公开页 |
|---|---|---|
| 实例 A | http://localhost:8000/ | http://localhost:8000/public |
| 实例 B | http://localhost:8001/ | http://localhost:8001/public |

两台实例挂载同一命名卷 `app_data`（容器内 `/data/app.db`），共享调查格值与公开记录；
重启后公开记录保留。`PEER_URL` 指定对端浏览器可达地址，供页面的「并行确认演示」使用。

### 本地运行（单实例）

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
```

库文件默认在 `./data/app.db`，可用环境变量 `DB_PATH` 覆盖。
`INSTANCE_LABEL`（实例名）与 `PEER_URL`（对端地址）仅用于界面展示与并行演示。

## 演示流程（内置示例数据）

示例数据（`sample_survey.csv`，2 分区 × 2 年龄组，人数均 10）：

| 分区 | 年龄组 | 人数 | 检出数 |
|---|---|---|---|
| 城东 | 青年 | 10 | **2**（受保护小样本格） |
| 城东 | 老年 | 10 | 8 |
| 城西 | 青年 | 10 | 8 |
| 城西 | 老年 | 10 | 8 |

1. 打开实例 A 的 `/`，点「导入示例数据」（导入后不可更换；实例 B 立即可见）。
2. 勾选「城东」+ 两个年龄组 → 预览（总数 10，安全）→ 确认发布。
3. 勾选两个分区 +「老年」→ 预览（总数 16）：单独看本安全，但与已发布的「城东」合并后，
   格「城东/青年」被约束到 **[0, 4]**（`城东合计10 − 城东老年≤10 ⇒ 城东青年≤4`，
   且 `老年合计16 ⇒ 城东老年≥6 ⇒ 城东青年≤4`），不再保留「≥5」的可行解 → 审查不通过。
4. 确认发布 → 按最新公开记录重核，返回 409 并列出受影响格与可行范围。
5. 改发「青年」（总数 10）：与已公开记录合并仍安全 → 发布成功。
6. 打开公开页 `/public`：只有人数表与获准汇总，无格内检出数。

### 并行确认演示（两台实例）

在任一实例的 `/` 页面底部「5. 双实例并行确认演示」：

- 点「填入合并不安全的窗口」：窗口 A = 城东 × {青年,老年}，窗口 B = {城东,城西} × 老年。
- 点「同时向两台实例确认发布」：页面用 `Promise.all` 同时向本实例与 `PEER_URL`
  发起确认。结果应为 **一份 201、一份 409**，409 一方列出「城东/青年 可行范围 [0,4]」。
- 点「填入合并安全的窗口」（城东全年龄 / 城西全年龄）再并行确认：**两份都应为 201**。

两实例分别直接打开 http://localhost:8000/ 与 http://localhost:8001/ 也各自可操作；
页面左上角显示当前实例名。

## 安全模型

- 未知量：每格一个整数 `x_i`，约束**仅**来自
  1. 界限 `0 ≤ x_i ≤ 人数_i`；
  2. 历次公开记录：所选交集格之和 = 公开总数；
  3. 候选发布：所选交集格之和 = 候选总数。
- 判定：对每个原检出数为 1~4 的格，须同时存在 `x_i = 0` 与 `x_i ≥ 5` 的可行整数解，
  否则拒绝并给出该格可行范围（z3 Optimize 求 min/max）。
- 求解在工作线程执行（每评估独立 z3 Context，线程安全），求解期间公开页与其他发布可用。

## 跨进程一致性（本次修复的核心）

原先的发布互斥是进程内 `asyncio.Lock`：两个服务进程各自加锁，彼此不可见，
两个「各自安全、合并不安全」的窗口可能都被写入。

修复后：

- SQLite 以 **WAL** 运行，读（公开页、预览）不阻塞写；公开页在他人确认发布期间仍可读取。
- 确认发布走 `publish_guarded()`：在 **`BEGIN IMMEDIATE` 写事务**内
  ① 取得数据库级写锁 → ② 重读**最新**公开记录 → ③ 重新求解审查 →
  ④ 通过才插入并 `COMMIT`。
  - 后取得写锁的进程一定能看到先提交的记录，因此**合并不安全时只可能有一份发布**；
  - 未通过审查只做内存判定，**不写入任何内容**，返回 409 + 受影响格与可行范围；
  - 任何异常都显式 `ROLLBACK`，进程崩溃时 SQLite 亦回滚未提交事务，
    **不会留下半次发布**。
- 导入同样在写事务内「判空 + 写入」，两实例并发导入只有一个成功，另一个 409，不留部分写入。
- 写锁等待超时（`busy_timeout`）返回 503「未产生任何发布记录，请重试」。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/import` | 导入调查 CSV（multipart，仅一次，导入后不可更换） |
| GET | `/api/admin/state` | 内部状态（含格内检出数、实例名、对端地址） |
| POST | `/api/preview` | `{districts, age_groups}` → 交集总数 + 安全评估 |
| POST | `/api/publish` | 写事务内重核后发布；不安全返回 409 + 受影响格与可行范围 |
| GET | `/api/public` | 公开数据：仅人数与获准汇总 |

CSV 表头：`分区,年龄组,人数,检出数`（亦兼容 `district,age_group,population,detected`）。
校验：≤16 格；人数 ≥5；检出数为 0~人数整数；（分区,年龄组）唯一。

## 已知限制

- 未实现认证/授权：内部台与接口对任何可达者开放，生产部署须自行加访问控制。
- 为保证演示页面能跨实例调用，CORS 设为 `allow_origins=["*"]`；生产应限制来源。
- 跨进程互斥依赖 SQLite 的单写者模型与共享文件系统（compose 命名卷满足）。
  若改用多主机/网络文件系统，需换用数据库服务器或分布式锁。
- 审查基于精确整数可行域（z3），非差分隐私；它保证「小样本格不被公开信息钉死」，
  不量化其他泄露渠道。
